Etch A Sketch on FPGA (VHDL)

Complete digital Etch A Sketch on a DE10-Nano board: rotary encoders, 720×480 HDMI controller, dual-port frame memory and screen clearing, designed in VHDL, simulated and validated on the board.
Published

October 2026

At a glance

Context FPGA lab project, ENSEA, 2026–2027
Team 2 students
Hardware DE10-Nano board (Intel Cyclone V SoC FPGA 5CSEBA6U23I7), mezzanine board with 2 rotary encoders and 10 LEDs
Tools VHDL, Quartus Prime, NVC and Surfer (simulation), VLC with an HDMI-to-USB capture adapter
Result Complete Etch A Sketch: drawing at 720×480 over HDMI, persistent strokes, clear button

Goal

Build a digital version of the Etch A Sketch: two rotary knobs move a pen that draws on a screen. Here the knobs are two rotary encoders and the drawing is shown on the board’s HDMI output.

The project was built block by block, each time following the same method: schematic, VHDL, simulation, then test on the board.

Architecture

1. Rotary encoders

A rotary encoder outputs two signals, A and B, shifted by a quarter period: the order in which they change gives the direction of rotation. The decoder detects edges on A and B and increments or decrements a counter of configurable width.

  • Synchronisation: A and B are not synchronised to the FPGA clock, so they go through two flip-flops before any edge detection, to avoid metastability.
  • Debouncing: on the board, a single notch sometimes moved the counter by several steps. The mechanical contacts bounce for a few milliseconds, and at 50 MHz each bounce looks like a real edge. A G_TICK_DIV generic subsamples A and B every 1 ms, which removes the bounce without missing any notch.
  • Validation: the counter is first wired to the 10 LEDs to read its value in binary on the board.

2. HDMI controller

The controller produces no colour: it scans the screen pixel by pixel and reports at each clock cycle where it is. It relies on two counters, a horizontal one (858 cycles per line) and a vertical one (525 lines per frame). The scanned area is larger than the 720×480 image: the invisible blanking areas are part of the standard and let the screen recognise the 480p mode.

A frame is 858 × 525 = 450,450 cycles, i.e. 16.7 ms at 27 MHz: 60 frames per second.

The frame memory is stored row by row: the address of pixel (x, y) is x + y × 720, from 0 to 345,599.

To test the controller on the board, its counters are wired straight to the colours: red follows x and green follows y. On 8 bits the value wraps every 256 pixels, hence the tiles.

3. Moving a pixel

A single white pixel is displayed at the encoders’ position. A register had to be added so that the colour arrives in the same cycle as the Data Enable signal, and the encoders were moved to the 27 MHz pixel clock so that the whole design runs on a single clock.

4. Persistent drawing

For the pen to leave a trail, the image is stored in a dual-port memory with one cell per pixel:

  • port A writes white at the cursor position;
  • port B reads, in parallel, the cell of the pixel being scanned and directly gives the colour sent to the screen.

At 24 bits per pixel (about 8.3 Mbit), the image would not fit in the FPGA’s memory blocks (about 5.5 Mbit), so each cell uses 8 bits. The memory’s one-cycle read latency replaces the register of the previous step and keeps the image aligned.

5. Clearing the screen

Pressing the left encoder’s button clears the screen. Since port B is reserved for display, clearing goes through port A, which then has two masters: the encoders in normal operation, and a counter that sweeps every address during clearing. A s_clearing signal selects between them by switching the address, data and write-enable together.

Clearing takes 345,600 / 27 MHz ≈ 12.8 ms, less than one frame, so it looks instantaneous. The pen stays where it is and drawing can resume immediately.

Takeaways

  • Any signal coming from outside must go through flip-flops before being used.
  • A signal assigned in a process changes on the next clock edge, which explains the one-cycle offsets that must be compensated.
  • A passing simulation does not guarantee real-world behaviour: encoder bounce only showed up on the actual board.
